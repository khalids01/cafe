# Taste
- When resuming unfinished work (e.g. handed off mid-task from another agent), do a read-only assessment first: read the progress doc, review the staged changes (`git diff --cached`), then report what's done, what's incomplete, and whether the step can be completed — before making any code changes. Confidence: 0.9
- Signals work-in-progress through git staging: stages partial changes and expects them reviewed via `git diff --cached` rather than relying on chat summaries. Confidence: 0.8
- Works across multiple coding agents and, when switching, asks for an explicit handoff ("give me a hands off so i can continue to another coding agent") — wants the current state written to a durable file the next agent can pick up without re-deriving setup (what's done, exact commands, environment prerequisites, gotchas, remaining steps), not just a chat summary. Confidence: 0.65
- Drives multi-step features from progress docs (e.g. `docs/ecommerce-todo-progress-v2.md`); check work against the doc's steps and acceptance criteria. Confidence: 0.7
- Treats edits as opt-in by default: states standing rules like "don't change anything unless I say so" — verify/investigate and report first, and only modify code or files once given explicit per-task authorization. Confidence: 0.9
- Follows a command-ownership agreement: the agent may run codegen (e.g. `prisma generate`) and checks (typecheck, focused tests, builds), but DB migrations are fully off-limits — the user explicitly instructed "don't run db migration or create sql", so never run `prisma migrate` and never even create the migration SQL files; the user creates and applies them (RBAC seed runs likewise reserved for the user). This governs the primary/dev database; for the isolated E2E database the user will grant one-off approval for schema/seed housekeeping to unblock a run — the agent was allowed to run `prisma migrate deploy` on `e2e_ecommerce`, reseed the RBAC catalog, and regenerate persona sessions. Also off-limits without explicit approval: database resets, broad seeds, and live courier/payment/email operations — courier/demo flows must use local simulator fixtures and genuine persisted state, never live external requests. Confidence: 0.9
- Wants direct, structured verdicts: a clear yes/no on feasibility plus explicit "done" vs "incomplete" breakdowns before proceeding. Confidence: 0.8
- For demo/tutorial videos, favors capturing the genuine live workflow (e.g. an E2E run with Playwright `recordVideo` plus an injected synthetic cursor overlay) over stacking screenshots into a slideshow — authenticity of real motion and cursor travel matters more than a pre-baked frame deck. Confidence: 0.75
- When a tutorial's narration is clear, does not want subtitles burned into the video (they looked oversized/bad) — keep captions as a sidecar track (e.g. `captions.vtt`) rather than rendering them into the frames. Confidence: 0.75
- Wants realistic, human-sounding names in demo/tutorial content (product, category, brand, warehouse, customer, carrier, tracking/payment references) instead of obvious placeholders like "Tutorial Golden Honey" / "Tutorial Courier". Confidence: 0.8
- For demo recordings, wants dev-only rendering artifacts eliminated — e.g. the ~1s flash where an unstyled oversized logo shows before CSS loads in `vite dev`; prefer recording against a built/served production-style build, and optionally also harden the app (give images/SVGs explicit dimensions) so even dev can't flash it. For this repo's two build modes, prefer recording against the **e2e build** (built with `tests/env/.env`, same isolated E2E database and personas the recorder uses), not the `:production` build. Standing capture spec: 1440×900, light theme, fully settled screenshots (no navigation/loading frames or CSS flashes) — never dev/Vite footage. Confidence: 0.7
- For tutorial/explanation videos, wants the element currently being narrated visually emphasized and synchronized with the audio — highlight/spotlight the relevant UI element (dim the rest) and point the cursor at it, not just perform the actions. Confidence: 0.85
- Reviews the finished deliverable himself and expects it to actually reflect the changes: after editing code, regenerate/re-render the shipped artifact (e.g. re-record the tutorial) so the output matches before declaring it done — code-only changes reported as complete read as "did you change anything?". Confidence: 0.7
- For demo/tutorial recordings, wants human-like navigation: drive page-to-page transitions through the visible UI (visible cursor travel + click ripple/links) instead of silent `page.goto()` jumps, so viewers can see how the flow moves from one screen to the next ("navigate like human", don't just swap pages automatically). Confidence: 0.8
- For demo/tutorial recordings, wants consistent, tight pacing — no perceptible stalls or dead air at transitions (e.g. a static ~24s tail at the end) and no full-page flashes from `page.reload()` when the UI updates in place. Confidence: 0.75
- For tutorial highlights, wants fine-grained, cue-synced beats — the spotlight and cursor should move field-by-field with the narration (highlight the slug input while it talks about the slug, move to Brand when it says "select a brand", then Featured/Trending, SEO title, SEO description, then Save) instead of holding one highlight on a single endpoint element (e.g. "Save basics") for a whole form segment. Confidence: 0.8
- For narration-driven tutorial videos, wants strict show-vs-say parity — "show and say the same thing": every action the narration describes must actually be visible on screen at that moment (e.g. the field being typed/selected under its matching cue, the button being clicked), and nothing on screen should contradict the narration (e.g. pre-filling all values then only narrating them, or narrating "select a brand" over an already-populated field, counts as broken). Confidence: 0.75
- Only spotlight an element while the narration is actually about it — no stale or irrelevant highlight (e.g. don't leave the sidebar "Overview" item highlighted for the whole ~30s intro), and drop the highlight entirely when the narration isn't explaining any specific element. Confidence: 0.7
- Wants concise, bottom-line-first answers: when handed a long, exhaustive report he asks for the same thing "in few lines" or follows up with a blunt status question ("did u upload the videos?") — lead with the essentials (the yes/no status of the key completed actions, then at most top items) and keep prose short rather than dumping a full bulleted breakdown. Confidence: 0.7
- Before starting a change, wants the agent to restate/play back its understanding of the problem and confirm alignment (e.g. "before changing tell me did you understand the problem?") rather than jumping straight into edits. Confidence: 0.7
- Treats committing, pushing, uploading and publishing as explicit end-of-task authorizations he triggers ("good now make commit", "Do NOT upload, publish, commit or push unless I separately ask") rather than things the agent does spontaneously; when asked, a detailed conventional-commit style message (type + scope + body) is fine. Also avoid commits or shared-producer changes midway through capture/render, since source checks can invalidate artifacts — keep changes uncommitted until production completes. Confidence: 0.7
- Never print secrets or dump `.env` files; verify environment configuration by checking only key presence (e.g. grep for `^KEY=`) and reporting non-secret facts (DB name, redis prefix, feature flags) instead. Confidence: 0.85
- Does not want dependencies or new tools installed without asking — installation is opt-in and requires explicit approval, like other state-changing actions. Confidence: 0.7
- Requires genuine human acceptance of deliverables: never falsely set approval flags (e.g. `watchedWithAudio`, `approved`); the user personally watches/reviews each artifact and only their explicit acceptance authorizes publication. Confidence: 0.85
- Insists the running app actually target the intended isolated environment (verify API/DB/redis/brand rather than assume), and treats prepared plans as unverified until checked against real API responses and source. Confidence: 0.75
- Prefers idempotent, resumable tooling: rerunning a step should reuse existing receipts/pointer files (e.g. `last-render.json`) and must not create duplicates; never guess timestamps or reuse an older failed attempt; keep resumable receipts and never delete caches or locks blindly. Confidence: 0.7
- Respects process ownership: reuse correctly configured existing servers when available; otherwise start only task-owned servers, stop them when finished, never stop user-owned processes, and never leave new servers running. Confidence: 0.75
- Automated checks (frame comparison, diffs, status codes) do not substitute for personally inspecting every produced artifact (each screenshot, full video/audio playback). Confidence: 0.75
- Delegates large autonomous batches: a terse range command ("now make and upload the videos from 5 to 20", "make tutorial guide videos from 26 - 30") means produce the entire range end-to-end (fixtures, narration, capture, render, upload) without pausing for per-item sign-off, choosing throughput over gating each item, and continuing as far as external limits allow rather than stopping early. Confidence: 0.7
- Never guess identifiers (tutorial IDs, folder names, etc.) — look them up in the authoritative catalog/manifest (e.g. `tutorial/catalog.json`) before acting. Confidence: 0.85
- Never fabricate business state in the DOM for recordings — every on-screen example must be real, persisted data; when narration discusses a saved result, show an API-verified saved example, not an unsaved form. Confidence: 0.8
- A control walkthrough/capture must not submit business writes — demonstrating controls must not persist real changes. Confidence: 0.8
- Never use `.first()` to conceal ambiguous Playwright targets; fix the selector instead. Confidence: 0.85
- Cleanup discipline: verify marker ownership before deleting fixtures, never swallow cleanup errors, and never claim success when cleanup failed. Confidence: 0.85
- Minimal provisioning: never blindly provision unrelated shared data (users, roles, shipping settings, etc.); prepare only the marker-owned fixtures the task actually requires. Confidence: 0.85
- When an item is blocked, record the precise blocker and continue the remaining items rather than halting the whole task. Confidence: 0.85
- Derived tracking files (e.g. `tutorial/upload-ledger.json`) must be refreshed/regenerated from their actual sources (local files + saved receipts), never hand-edited or invented. Confidence: 0.8
- Stay in scope: do not add or run unrelated tests, and preserve unrelated work (including existing taste-file edits). Confidence: 0.8
- User runs core local services (PostgreSQL, Redis) in **podman** containers (moved off docker) and manages their lifecycle personally — detect and reuse them as user-owned infrastructure via `podman ps` and port checks, never stop/restart them, and when the user says services are up ("i just started redis and psql in podman... so continue"), verify connectivity and resume immediately without re-asking. Confidence: 0.85
- Every tutorial needs a `fixtures.local.json` before capture, including no-fixture tutorials — for those, write an empty scaffold (`{"marker": ..., "values": {}, "ownershipChecks": [], "outcomeChecks": [], "cleanup": []}`) or `produce.ts capture` fails; validate no-fixture tutorials via `bun --env-file=tests/env/.env tutorial/shared/cli.ts prepare <slug>`. Confidence: 0.85
- Running fixture scripts with bun: bun defaults `NODE_ENV=production` and overrides `--env-file`, so always prefix fixture/capture commands with explicit `NODE_ENV=test E2E_MODE=true` (plus `COURIER_WORKERS_ENABLED=false ENABLE_POLAR=false`) rather than relying on the env file alone. Confidence: 0.85
- Vision inspection of tutorial screenshots times out on full-size PNGs — downscale first with ffmpeg (720:450, then 480:300, then 360:225 or JPEG for stubborn frames), and if the vision service still times out, sleep 60–120s and retry since it recovers on its own. Confidence: 0.75
